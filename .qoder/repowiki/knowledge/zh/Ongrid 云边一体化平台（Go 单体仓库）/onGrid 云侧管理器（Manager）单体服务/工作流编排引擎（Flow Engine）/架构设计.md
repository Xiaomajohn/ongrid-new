模块按三层切分：
- `biz/flow` 业务层：`graph.go` 定义前端保存的 JSON 画布格式（GraphNode/GraphEdge），`ParseGraph`+`Validate` 是进入引擎的唯一入口，强制校验唯一 id、已知类型、端口合法性与无环；`engine.go` 实现确定性 DAG 调度——从 trigger 节点入队，OR-join + execute-once 语义，通过 `runState.executed` 去重，`sync.WaitGroup` 等待 fan-out，`chan struct{}` 限流到 `maxConcurrentNodes=4`，每节点 panic 被 recover 降级为 run 失败；`usecase.go` 暴露 CRUD / Trigger / TestNode / PruneOldRuns 等用例门面，并通过 `Repo`/`RunRepo` 接口与存储解耦；`noderegistry.go` 维护全局 `nodeRegistry`，每个 NodeSpec 声明 Kind/Category/Ports/ConfigFields/OutputShape/Execute，所有内置节点在 `init()` 中 `RegisterNode`，新增节点无需改核心；`nodes.go` 定义 `Executors` 缝合面（AgentRunner/LLMRunner/ToolInvoker/Notifier），零值即可测试。
- `server/flow/http.go` 薄 HTTP 层，chi 路由 + `requireWriter` 角色守卫，仅做 DTO 转换与错误码映射，不碰业务逻辑。
- `data/flow/store/` GORM 实现 `Repo`/`RunRepo`，`store.go` 负责 Flow/FlowRun/FlowRunNode 的增删改查与 `PruneRuns`/`SweepStaleRunning` 生命周期管理，`migrate.go` 提供建表迁移。
依赖方向：`server → biz → data/store`，`scheduler.go` 作为后台协程周期扫描 enabled flows 中的 `trigger.cron` 节点并调用 `Usecase.TriggerEvent`，`dispatcher.go`（告警触发）与之对称，二者都只读 Usecase，不直接访问存储。
