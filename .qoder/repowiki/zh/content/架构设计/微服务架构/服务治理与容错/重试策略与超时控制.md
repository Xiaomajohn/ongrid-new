## 简介
本文件聚焦 OnGrid 的重试策略与超时控制，围绕以下目标展开：
- 深入描述重试算法实现：线性退避、指数退避与固定间隔（含抖动）策略。

- 说明重试次数限制与最大等待时间控制。
- 提供重试流程图、退避算法图与超时配置示例。
- 阐述重试策略的配置方法与动态调整机制。

## 详细组件分析

### 告警投递重试工作器（线性退避）
- 策略要点
  - 线性退避：每次重试的最小间隔为“尝试次数 × 每尝试退避时长”。
  - 最大尝试次数：超过阈值不再重试。
  - 业务校验：若事件已解决或渠道被禁用，则终止重试并标记结果。
  - 幂等性：通过“投递记录 + 尝试计数”保证同一投递不会重复发送。
- 关键流程
  - 周期扫描失败投递 → 计算最小等待时间 → 重建消息 → 调用通知器 → 更新状态与事件。
- 配置项
  - 最大尝试次数、每尝试退避时长、Tick 频率、日志与时间源注入。

```mermaid
flowchart TD
Start(["开始"]) --> Scan["扫描可重试投递"]
Scan --> Backoff{"是否满足退避?"}
Backoff --> |否| Skip["跳过本次"]
Backoff --> |是| CheckBiz["业务校验(事件/渠道)"]
CheckBiz --> Resolved{"事件已解决?"}
Resolved --> |是| MarkSuccess["标记成功并结束"]
Resolved --> |否| Disabled{"渠道已禁用?"}
Disabled --> |是| MarkFailed["标记失败并耗尽预算"]
Disabled --> |否| Send["发送通知"]
Send --> Result{"发送成功?"}
Result --> |是| UpdateOK["更新成功/事件/标记已通知"]
Result --> |否| UpdateFail["更新失败/事件"]
UpdateOK --> End(["结束"])
UpdateFail --> End
MarkSuccess --> End
MarkFailed --> End
Skip --> End
```

### 隧道客户端（指数退避 + 自动重连）
- 策略要点
  - 首次拨号：指数退避，初始间隔与上限固定。
  - 连接建立后：底层库负责断线重连；上层在检测到路由失效时主动重拨。
  - 重拨超时：独立上下文设置上限，避免长时间阻塞。
- 关键流程
  - Dial 循环拨号 → 注册处理器 → 成功后返回；失败则指数退避并重试。
  - Call 失败检测 → 可能触发异步重拨 → 回调通知上层。

## 性能考量
- 线性退避适合“最终一致”的投递场景，避免对下游造成突发压力。
- 指数退避适用于网络波动与远端服务短时不可用，能有效降低重试风暴。
- 建议结合监控指标观察重试成功率、平均延迟与失败原因分布，动态调优退避步长与上限。

## 故障排查指南
- 告警投递未送达
  - 检查是否命中退避窗口与最大尝试次数。
  - 确认事件状态是否为“已解决”，渠道是否启用。
  - 查看重试事件与失败原因记录。
- 隧道无法建立或频繁重连
  - 关注首次拨号指数退避日志与错误码。
  - 检查是否出现路由失效导致主动重拨。
- 子进程频繁重启
  - 确认崩溃原因与退避上限是否合理。
- 数据库指标采集失败
  - 核对采集目标可达性与认证配置。
  - 观察退避曲线是否收敛。

## 结论
OnGrid 在不同子系统采用了差异化的重试策略：告警投递采用线性退避，确保稳定与可控；网络与进程级组件采用指数退避，提升弹性与自愈能力。配合明确的业务校验与最大尝试次数限制，系统在可靠性与资源占用之间取得平衡。通过合理的超时配置与动态调整，可在不同部署环境下获得更稳健的运行表现。

### 退避算法图（线性 vs 指数）
- 线性退避（告警投递）
  - 第 N 次重试至少在第 N×步长之后。
- 指数退避（隧道/子进程/采集/IM）
  - 间隔按倍数增长，直至达到上限。

```mermaid
flowchart TD
LStart["线性退避起点"] --> LN["第N次尝试"]
LN --> WaitL["等待 N * step"]
WaitL --> NextL["下一次尝试"]
IStart["指数退避起点"] --> IN["第N次尝试"]
IN --> WaitI["等待 base * 2^(N-1)"]
WaitI --> Cap{"超过上限?"}
Cap --> |是| UseCap["使用上限"]
Cap --> |否| NextI["下一次尝试"]
```
